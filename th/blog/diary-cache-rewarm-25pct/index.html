บันทึก token ของนักพัฒนาเกมคนเดียว

วันเดียว token รั่วไป 25% และ 14.4% หมดไปกับการอุ่นแคชใหม่

Justin Lee, Dumb Game Lab · 2026-11-18

วันที่ 28 ตุลาคม เราถูกคิด token ทั้งหมด 90.6M และ 22.7M (25%) ตกไปอยู่ในช่องที่สูญเปล่า ช่องที่ใหญ่สุดคืออุ่นแคชใหม่ 13.0M คิดเป็น 14.4% ของทั้งวัน หรือเกินครึ่งของส่วนที่เสียทั้งหมด สาเหตุคือแชตสองเซสชันที่เปิดจากมือถือค้างไว้ทั้งวัน และทุกครั้งที่ส่งข้อความเพิ่มอีกประโยค บทสนทนาก่อนหน้าทั้งหมดก็ถูกเขียนลงแคชใหม่ตั้งแต่ต้น

เริ่มจากบันทึกของวันนั้น

เราสร้างเกมด้วยการรัน AI agent หลายตัวทั้งวัน ตอนกลางคืนที่เขียนบันทึกประจำวัน เราจะรวบรวม log ของแต่ละเซสชันมาแยก token ของวันนั้นเป็นช่อง ๆ บันทึกวันที่ 28 ตุลาคมออกมาแบบนี้

ยอดที่ถูกคิดเงินรวม 90.6M มาจาก input 33K output 9.6M และเขียนแคช 80.9M แต่การเขียนแคชอย่างเดียวกินพื้นที่เกือบทั้งหมด ตอนเปิดบันทึกนี้ครั้งแรกเลยนึกว่าตัวเองคำนวณผิด เขียนแคชคิดเป็น 89.4% ส่วนอ่านแคช 2.61B ราคาต่อหน่วยต่ำ เราจึงไม่นับรวมในยอดนี้และจดแยกไว้

อุ่นแคชใหม่คืออะไร

AI แบบแชตจะอ่านบทสนทนาก่อนหน้าทั้งหมดใหม่ทุกครั้งที่เราส่งข้อความ prompt caching คือการเก็บส่วนที่ประมวลผลไปแล้วไว้ชั่วคราว เพื่อให้คำขอถัดไปดึงกลับมาใช้ได้ในราคาถูก

ปัญหาอยู่ที่ระยะเวลาเก็บ ตามเอกสารทางการของ Anthropic แคชมีอายุเริ่มต้น 5 นาทีและต่ออายุทุกครั้งที่ถูกใช้ และเลือกแบบ 1 ชั่วโมงได้ ถ้าเลยเวลานั้นแล้วค่อยส่งข้อความ บทสนทนาก่อนหน้าทั้งหมดต้องเขียนลงแคชใหม่

ราคาต่างกันมาก การเขียนแคชคิด 1.25 เท่าของราคา input พื้นฐาน (แบบ 5 นาที) หรือ 2 เท่า (แบบ 1 ชั่วโมง) ส่วนการอ่านแคชคิดแค่ 0.1 เท่า บทสนทนาเดียวกันถ้าเขียนใหม่จะแพงกว่าการอ่าน 12.5 ถึง 20 เท่า

ตัวการคือเซสชันในมือถือสองตัวที่เปิดทั้งวัน

บันทึกของเรานับเป็น “อุ่นแคชใหม่” เมื่อเซสชันหลักพักไปเกินหนึ่งชั่วโมงแล้วกลับมาเขียนบริบททั้งหมดลงแคชอีกรอบ วันนั้นช่องนี้บวมขึ้นเพราะเซสชันสองตัวที่เปิดค้างไว้ในมือถือ

ตัวหนึ่งเปิดอยู่ 1,379 นาที อีกตัว 1,161 นาที ในขณะที่หนึ่งวันมีแค่ 1,440 นาที แปลว่าทั้งสองหน้าต่างเปิดตั้งแต่เช้าและไม่เคยถูกปิดจริง ๆ เลยจนดึก เกือบทั้งวัน นึกอะไรออกก็พิมพ์ส่งจากมือถือทีละประโยค และทุกครั้งบทสนทนาที่เย็นไปแล้วก็ถูกอุ่นใหม่ตั้งแต่ต้น

จุดที่รั่วมากที่สุดคือเซสชันแก้คอขวดที่เริ่มด้วยคำถาม “ทำไมมันหยุดล่ะ” ภายใน 160 นาที เซสชันนี้ใช้ 4.8M ไปกับการอุ่นแคชใหม่ เกือบสองในสามของ 7.5M ที่เซสชันนี้ใช้ทั้งวัน

อันดับหนึ่งสี่วันติด ตั้งใจอย่างเดียวไม่ลด

อุ่นแคชใหม่เป็นช่องที่สูญเปล่ามากที่สุดสี่วันติดกันตั้งแต่ 25 ตุลาคม เราจดลงบันทึกทุกวันและเปิดตั๋วไว้ให้แก้ด้วย ถึงอย่างนั้นตัวเลขก็ไม่ลง

คำสัญญากับตัวเองว่า “ใช้เซสชันสั้น ๆ” ลืมทันทีที่หยิบมือถือขึ้นมา ระหว่างเดินทางถ้านึกงานอะไรออกแล้วอยากสั่งเลย พิมพ์ต่อในหน้าแชตที่เปิดอยู่อีกประโยคง่ายกว่าเปิดหน้าใหม่แล้วอธิบายทุกอย่างตั้งแต่ต้นเยอะ กฎที่พึ่งนิสัยคนจะรั่วซ้ำที่เดิมไปเรื่อย ๆ

ช่องที่สอง ไม่ได้ merge 6.7M

อันดับสองของความสูญเปล่าคือไม่ได้ merge 6.7M (7.4%) ช่องนี้นับเซสชันที่ใช้ token ไปเยอะแต่ผลงานไม่เคยเข้าโค้ดหลักเลยสักครั้ง

เซสชันสถานะโซล (103 นาที) กับเซสชันชิชิตะลุมบอน (47 นาที) ตกอยู่ในช่องนี้ ฝั่งโซลส่งงานต่อให้ sub-agent ตอบว่า “กำลังทำอยู่” แล้วจบไปเฉย ๆ ถ้ารวมไม่ได้ merge กับอุ่นแคชใหม่ เซสชันสถานะโซลใช้ไป 2.4M

สิ่งที่เราเปลี่ยน

บทเรียนข้อแรกในบันทึกวันนั้นคือความยาวของเซสชันไม่ลดลงเพราะคำพูด เราจึงเลือกติดตั้งกลไกแทนการตั้งใจ เมื่อเซสชันเกินเวลาที่กำหนด มันจะสรุปเนื้อหาทั้งหมดจนถึงตอนนั้นเก็บไว้แล้วย้ายไปเซสชันใหม่

เซสชันใหม่เริ่มด้วยสรุปสั้น ๆ อันเดียว บทสนทนาที่ต้องอุ่นใหม่จึงเล็กมาก ถ้าเจอปัญหาแบบเดียวกัน แนะนำให้วัดตามลำดับนี้ก่อน

  • จด token รายวันแยกเป็น input output เขียนแคช และอ่านแคช
  • ถ้าสัดส่วนเขียนแคชสูง ให้สงสัยบทสนทนาที่กลับมาคุยต่อหลังพักก่อน
  • นับจำนวนนาทีของเซสชันที่เปิดค้างนานที่สุด
  • เซสชันที่เกินเวลาที่กำหนดให้ทิ้งสรุปไว้แล้วเปิดใหม่
  • ถ้าช่องเดิมขึ้นอันดับหนึ่งหลายวันติด เลิกตั้งใจแล้วติดกลไกแทน

FAQ

prompt caching คืออะไร

คือฟีเจอร์ที่เก็บส่วนต้นของ prompt ที่ประมวลผลไปแล้วไว้ชั่วคราว เพื่อใช้ซ้ำในคำขอถัดไป ตามเอกสารของ Anthropic อายุเริ่มต้นคือ 5 นาที ต่ออายุทุกครั้งที่ใช้ และเลือกแบบ 1 ชั่วโมงได้

ค่าใช้จ่าย prompt caching ต่างกันแค่ไหน

ตามตัวคูณในเอกสารทางการ เขียนแคชคิด 1.25 เท่าของราคา input พื้นฐาน (5 นาที) หรือ 2 เท่า (1 ชั่วโมง) และอ่านแคชคิด 0.1 เท่า เขียนเนื้อหาเดิมซ้ำจะแพงกว่าอ่าน 12.5 ถึง 20 เท่า

ทำไมเปิดเซสชัน Claude Code ค้างไว้นานแล้วเปลือง token

เพราะถ้าส่งข้อความหลังแคชหมดอายุ บทสนทนาก่อนหน้าทั้งหมดจะถูกเขียนลงแคชใหม่ กรณีของเรา เซสชันในมือถือสองตัวที่เปิดทั้งวันทำให้ 13.0M จากยอดทั้งวัน 90.6M หมดไปแบบนี้

ดูการใช้ token ของ Claude Code ได้อย่างไร

เรารวบรวมไฟล์ log เซสชัน Claude Code ที่อยู่ในเครื่องเป็นรายวัน แยกเป็น input output เขียนแคช และอ่านแคช แล้วนับช่องที่สูญเปล่าแยกไว้ เช่น การเขียนแคชหลังพัก หรือเซสชันที่จบโดยไม่มีผลงาน ต้องเห็นตัวเลขแยกตามช่องถึงจะรู้ว่ารั่วตรงไหน ตอนดูแค่ยอดรวม รู้แค่ว่าใช้เยอะแต่ไม่รู้ว่าเพราะอะไร

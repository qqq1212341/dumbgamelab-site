Satu alarm menghabiskan batas baca 5 juta baris per hari: melacak error 1101 Durable Objects

Justin Lee, Dumb Game Lab · 2026-11-10

Pada 7 November server pengumpul error mulai mengembalikan error 500 dengan kode 1101 dan pesan «Exceeded allowed rows read». Pelakunya alarm yang berjalan setiap 5 detik di server game (도트혈맹) pada akun yang sama. Alarm ini memindai tabel users dan feed tanpa index, dan sendirian membaca 4.98 juta dari batas 5 juta baris per hari. Batas itu dipakai bersama oleh seluruh akun, jadi server undangan teman dan server pengumpul error ikut mati. Saya memperbaikinya dengan 2 index dan cache 10 menit. Sekarang setiap jam saya mengukur baris yang dibaca tiap server, dan kalau lewat 60% muncul notifikasi lengkap dengan nama pelakunya.

Awalnya saya curiga ke server yang salah

Gejalanya muncul lebih dulu di server pengumpul error. Memanggil daftar sesi dan daftar issue sama-sama menghasilkan 500, dan isi responsnya hanya error code: 1101. Pada waktu yang sama server undangan teman juga mati dengan kode yang sama.

Bilah peringatan darurat menulis server undangan teman sebagai pelaku. Artinya server yang mati langsung ditulis sebagai pelaku. Padahal server undangan hanya menerima beberapa ribu request per hari, tidak mungkin menghasilkan pembacaan sebanyak itu.

Server pengumpul error juga begitu. Request hanya 2-3 ribu per hari, tetapi baris yang dibaca 1.4 juta sampai 5.14 juta. Kalau jumlah request dan baris yang dibaca tidak cocok sejauh itu, berarti bukan request yang membaca, tetapi ada pihak lain.

Pelakunya alarm 5 detik

Batasnya dipakai bersama seluruh akun, jadi saya harus melihat pemakaian per server. Saya ambil baris yang dibaca tiap server (worker) lewat Cloudflare API, dan hampir semuanya ada di satu tempat: server game 도트혈맹.

Server ini punya alarm yang berjalan setiap 5 detik. Di dalam alarm ada query yang menghitung jumlah orang yang sedang online dan membaca daftar bot. Tabel users dan feed tidak punya index, jadi setiap kali query memindai tabel dari awal sampai akhir.

290 baris sekali jalan terlihat kecil. Tetapi alarm berjalan 17,280 kali sehari, dan hasil kalinya 4.98 juta.

Yang saya perbaiki

Saya memperbaiki server 도트혈맹 dan server pengumpul error masing-masing. Penyebab keduanya sama: query rentang tanpa index.

  • Setelah perbaikan di-deploy, batas hari itu sudah telanjur habis sehingga server tidak langsung hidup. Server pengumpul error baru pulih pada reset berikutnya (00:00 UTC).
  • Dengan index, baris yang dibaca sekali jalan turun dari ukuran seluruh tabel menjadi sebanyak baris yang memang dibutuhkan.

Supaya tidak terulang

Memperbaiki saja tidak cukup. Kali ini saya baru tahu setelah batas habis, dan baru lama kemudian tahu siapa yang menghabiskannya. Jadi saya menambahkan dua hal.

Pertama, tes. Alarm dijalankan 400 kali, query yang dieksekusi dikumpulkan, lalu rencananya dilihat dengan EXPLAIN QUERY PLAN. Kalau ada satu saja query yang memindai users atau feed tanpa index, tes gagal. Query yang memakai LIMIT dan berhenti lebih awal dikecualikan.

Kedua, pemantauan. Setiap jam pada menit ke-7, baris yang dibaca semua server dijumlahkan, dan kalau lewat 60% dari batas, notifikasi dikirim lengkap dengan nama server pelaku dan jumlah barisnya. Saya juga menembak langsung server undangan dan server pengumpul error, kalau keluar 1101 itu juga dilaporkan, dan dicabut kalau sudah pulih.

Yang saya salah

Yang salah bukan satu query. Beberapa server berbagi satu batas gratis, tetapi tidak ada tempat yang mengukur berapa yang dibaca tiap server. Kalau satu server menghabiskan batas, server yang tidak bersalah mati menggantikannya, dan kita hanya melihat yang mati.

Karena itu di 도트혈맹 saya menambahkan tes yang memeriksa apakah query di jalur alarm memakai index. Dari kejadian ini saya belajar bahwa kalau batasnya dipakai bersama satu akun, tabel pemakaian per server harus ada lebih dulu.

FAQ

Apa arti error Cloudflare Durable Objects 1101?

Bisa berarti batas gratis terlampaui. Pada kasus saya, isi responsnya juga memuat «Exceeded allowed rows read», artinya batas baris yang dibaca per hari (5 juta baris untuk seluruh akun) sudah habis.

Apakah batas baca Durable Objects berlaku per server atau per akun?

Di akun saya, seluruh akun berbagi 5 juta baris per hari. Karena itu ketika satu server memakai hampir semuanya, dua server lain ikut berhenti.

Kalau batas sudah habis, apakah server langsung hidup setelah diperbaiki?

Tidak langsung. Walau sudah diperbaiki dan di-deploy, batas hari itu tetap sama, jadi saya harus menunggu reset 00:00 UTC (pukul 9 pagi waktu Korea).

Bagaimana cara tahu alarm memindai seluruh tabel?

Kumpulkan query yang dijalankan di dalam alarm lalu jalankan EXPLAIN QUERY PLAN. Kalau rencananya memuat SCAN nama_tabel tanpa index, berarti seluruh tabel dibaca.
